{{- /* What every newsletter shortcode does on a site that has the feature switched off: it says so, by name and by page, and fails the build. The alternative — render nothing and carry on — is how a theme earns the question "I wrote the shortcode and nothing appeared, why?". Nobody can answer it from the page: the markup is correct, the shortcode exists, and the reason is a boolean in a config file the author may not own. A build that explains costs one line in a log; a silent one costs a support thread. It is an erroridf rather than an errorf so the master switch stays a switch. Pulling `enable` on a live site — the endpoint is down, the engine is being replaced, a lawyer asked — must not turn into editing every guide that carries a block first; the message names the config line that suppresses it, and suppressing it is the deliberate half of a deliberate act. Context: a dict page — logical path of the page the shortcode was written on. sc — the shortcode's name, as the author typed it. */ -}} {{- erroridf "newsletter-disabled" `newsletter: {{< %s >}} on page %q rendered nothing, because params.newsletter.enable is false. The feature is off by default and needs three things outside the theme before it works: a sending engine, an endpoint of your own to post to, and a bot check in front of it (docs/newsletter.md). Turn it on, or delete the shortcode — or, if the switch was pulled on purpose and the content is meant to keep it, silence this build error with ignoreLogs = ["newsletter-disabled"] in your config.` .sc .page -}}
